# lowacal (C++ rewrite)

Мінімалістичний, дистро-агностик десктопний календар: C++/Qt6/QML
(Kirigami), CalDAV-синхронізація (iCloud з коробки, будь-який інший
CalDAV-сервер теж), фонова синхронізація і нотифікації без відкритого
вікна, ховається в трей замість закриття процесу.

## Чому C++, а не Rust

Попередня версія була на Rust + `cxx-qt`. Після кількох раундів багів,
усі — на межі Rust↔Qt (версійний дрейф bridge-макроса, `cxx-qt-lib` не
покриває QtWidgets, звідси зламаний трей), а не в самій CalDAV/ICS/SQL-
логіці, вирішили переписати напряму на C++/Qt6: без проміжного шару,
який сам ще й "in early development and the API changes frequently"
(цитата з README `cxx-qt`).

Бонус, якого не було зпочатку: QML (уся Kirigami-верстка, яку вже
налагодили в Rust-версії) переноситься майже без змін — QML не знає і
не дбає, якою мовою написаний хост-процес.

## Стан проєкту — і чому цій версії можна довіряти більше

На відміну від Rust-версії (де через застарілий Rust у пісочниці вдалось
реально скомпілювати тільки мінімальний smoke-test), тут пісочниця мала
повний Qt6 + CMake + сучасний GCC без жодних версійних обмежень. Це
дозволило зробити повноцінну перевірку:

- **Весь проєкт (усі .cpp, увесь QML) реально компілюється й лінкується**
  в один бінарник — не мінімальний тест, а повний застосунок з усіма
  класами (CalDavClient, Database, IcalParser, CalendarBridge,
  TrayController, SyncWorker) та всіма шістьма QML-файлами, включно з
  `main.qml`, що використовує `Kirigami.ApplicationWindow`.
- **Застосунок реально запускався** (headless, `-platform offscreen`) і
  доходив до моменту завантаження QML — падає рівно на
  `module "org.kde.kirigami" is not installed`, бо KF6 Kirigami не
  пакетований для Ubuntu 24.04 (тільки старий Qt5-варіант). Це єдина
  межа, за яку не вдалось зазирнути в цій пісочниці — усе до неї
  підтверджено роботою, не здогадом.
- Заради додаткової певності тимчасово підмінили Kirigami на звичайний
  `QtQuick.Controls` і застосунок **реально пропрацював кілька секунд**:
  QML завантажився, `CalendarBridge` створився і відповідав на виклики,
  фоновий потік (`SyncWorker`) стартував, трей-іконка створилась.
  Kirigami-версію повернули одразу після цього тесту.
- **`tests/logic_test.cpp`** — окремий, не-QML тест, що напряму дергає
  `IcalParser` і `Database` з реальними даними (кирилиця, коми,
  апострофи, лапки-ялинки, перенос рядка в описі, RFC 5545 line-folding,
  all-day-детекція, SQL JOIN-запити). **26 з 26 перевірок пройшли.**
  Це найсильніша перевірка з усієї історії цього проєкту — саме тут, у
  парсингу/генерації ICS, найбільша ймовірність тонких багів, і вона
  реально протестована, не тільки скомпільована.

Це не означає "нуль багів" — Kirigami-специфічні деталі (точні назви
властивостей у твоїй версії KF6) і реальний CalDAV-раунд-тріп з живим
iCloud так само не перевірені, як і в Rust-версії. Але площа
непідтвердженого коду тепер значно менша.

## Архітектура

- **Один процес**, `QThread` для фонової синхронізації (`SyncWorker`),
  замість окремого демона — та сама логіка, що й у Rust-версії.
- **SQLite — єдине джерело правди для UI**, два `QSqlDatabase`-з'єднання
  (по одному на потік — GUI-потік для `CalendarBridge`, робочий потік для
  `SyncWorker`), обидва на той самий файл, WAL-режим робить це безпечним.
- **Справжні push-оновлення, не поллінг.** Це реальне архітектурне
  покращення порівняно з Rust-версією: там QML доводилось опитувати
  бридж на таймері, бо я не був певен API `cxx_qt::Threading` для
  крос-потокового виклику. Тут — звичайний Qt: `SyncWorker` емітить
  сигнал, Qt сам маршалить його на GUI-потік (`Qt::QueuedConnection`,
  автоматично для міжпотокових з'єднань), `CalendarBridge` перевипромінює
  `eventsChanged()`, QML слухає напряму через `Connections{}`. Без жодних
  таймерів на 300мс/2с/15с, які були в Rust-версії.
- **Трей — нативний `QSystemTrayIcon`**, живе на GUI-потоці, тому
  "показати вікно" — це пряме з'єднання сигнал→лямбда в `main.cpp`, без
  потреби опитувати прапорець (як доводилось робити з `ksni` в Rust-
  версії, де трей жив на фоновому потоці окремо від Qt).
- **Закриття вікна ховає його, не завершує процес** (`main.qml`,
  `onClosing`) — той самий підхід, що й раніше.

## Збірка (Arch Linux)

```bash
sudo pacman -S cmake qt6-base qt6-declarative qt6-tools kirigami sqlite qtkeychain-qt6

cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)

# Встановлення в ~/.local (бінарник у ~/.local/bin, .desktop у
# ~/.local/share/applications) - після цього застосунок запускається як
# `lowacal` звідусіль, з'являється в меню програм, і нотифікації
# коректно прив'язуються до нього (лишаються в історії сповіщень):
cmake --install build

lowacal   # або, як і раніше, ./build/lowacal без встановлення
```

Якщо `lowacal` після install не знаходиться - перевір, що `~/.local/bin`
у `$PATH` (`echo $PATH`); на більшості дистрибутивів так і є, але fish
іноді треба `fish_add_path ~/.local/bin`.

Для незалежного тесту ICS/SQL-логіки (не потребує Kirigami, корисно як
швидка перевірка після будь-яких змін у `icalparser.cpp`/`database.cpp`):

```bash
cmake -B build -DLOWACAL_BUILD_TESTS=ON
cmake --build build --target lowacal_logic_test
./build/lowacal_logic_test
```

## Flatpak

Основний спосіб дистрибуції: один пакет для будь-якого дистрибутива.
Маніфест — `io.github.detcom_gh.lowacal.yml` (рантайм KDE 6.10 з Kirigami;
QtKeychain збирається окремим модулем, бо в рантайм не входить).

```bash
sudo pacman -S flatpak-builder
flatpak remote-add --if-not-exists --user flathub https://dl.flathub.org/repo/flathub.flatpakrepo
flatpak-builder --user --install-deps-from=flathub --install --force-clean \
    build-flatpak io.github.detcom_gh.lowacal.yml
flatpak run io.github.detcom_gh.lowacal
```

Перша збірка довга: завантажується KDE SDK (кілька ГБ, один раз).

Що варто знати:
- Flatpak-версія має **окремі дані** від звичайного встановлення
  (`~/.var/app/io.github.detcom_gh.lowacal/`), тож акаунт там додається заново.
- Дозволи мінімальні: мережа, нотифікації, трей, сховище паролів. Доступу
  до файлів і звуку нема.
- Автозапуск у Flatpak іде через системний Background-портал: GNOME може
  один раз спитати дозвіл, Plasma дозволяє одразу.

**До публікації на Flathub лишається:** публічний репозиторій
`github.com/Detcom-GH/lowacal`, тег релізу (джерело в маніфесті
переключається з локальної теки на git-тег, приклад у коментарі), і три
скріншоти в `screenshots/` (`month.png`, `week.png`, `add-account.png`),
на які вже посилаються метадані `data/lowacal.metainfo.xml.in`.

## Брендинг

- **Іконка** (`data/icons/lowacal-<розмір>.png`): лого з таксою, вписане в
  квадратну базову форму офіційної сітки Flathub (плитка займає 80,5%
  полотна, як вимагає правило про розмір), без запеченої тіні, з тонким
  кантом для контрасту на світлому тлі. Встановлюється в тему іконок
  розмірами 32–512.
- **Трей** (`data/icons/lowacal-tray.svg` → PNG): спрощений гліф — лише
  календар із лого, фірмовий фіолетовий `#5E458D`. Повне лого на 22 px
  нечитабельне.
- **У вікні:** без картинок — такса, намальована символами
  (малюнок у `data/dachshund.txt`, показує `qml/AsciiDachshund.qml` системним моноширинним шрифтом), у шапці
  сайдбару і у вікні «Про Lowacal» (Налаштування → «Про програму»).
- Акцентний колір інтерфейсу навмисно лишається системним (як у всіх
  KDE-застосунках); фіолетовий живе в лого та іконці трею.

## Запуск при вході в систему

Налаштування → «Запускати автоматично при вході в систему (у треї)».
Застосунок стартує з `--hidden`: без вікна, одразу в треї, і нагадування
працюють з першої хвилини після входу. Якщо копія вже запущена, повторний
запуск із меню просто відкриває її вікно, а не створює другу копію з
другим треєм.

## Додавання календарів

Усе через інтерфейс, без конфіг-файлів і терміналу: кнопка **«Додати
календар»** (або «Додати акаунт» у сайдбарі) → обрати провайдера → кілька
полів → «Підключити».

- **iCloud**: Apple ID + *пароль програми*. Діалог пояснює, що це, і
  кнопкою відкриває потрібну сторінку Apple.
- **Будь-який CalDAV** (Nextcloud, Fastmail, Baïkal, Radicale, mailbox.org…):
  достатньо адреси самого сервера (`cloud.example.com`), правильний шлях
  до календарів знаходиться автоматично (`/.well-known/caldav`, типові
  шляхи Nextcloud/Baïkal, редиректи).
- Дані перевіряються на сервері **до** збереження: невірний пароль чи
  неправильна адреса дають зрозуміле повідомлення в самому діалозі.
- Паролі зберігаються в системному сховищі (KWallet / GNOME Keyring /
  будь-який Secret Service) через QtKeychain, ніколи у файлах застосунку.
  При першому збереженні KWallet може один раз спитати дозвіл: це нормально.
- Видалити акаунт: меню «⋯» біля його назви в сайдбарі. На сервері нічого
  не видаляється.

- **Google Календар**: кнопка «Увійти через Google» відкриває сторінку
  Google у браузері; пароль вводиться там, застосунок його не бачить.
  Зберігається лише токен доступу до календаря, у системному сховищі.

## Google: одноразове налаштування для того, хто збирає застосунок

Google не приймає паролі від сторонніх програм: застосунок має бути
зареєстрований у Google Cloud і отримати власні ідентифікатори. Без них
усе збирається й працює, а пункт Google показується як недоступний.

1. https://console.cloud.google.com → створити проєкт (наприклад «Lowacal»).
2. APIs & Services → Library → знайти **CalDAV API** → Enable. Саме CalDAV
   API: окремий від «Google Calendar API» пункт, без нього буде відмова 403.
3. Екран згоди OAuth (Google Auth Platform): тип External, назва застосунку,
   контактна пошта; у дозволах (Data access) додати
   `https://www.googleapis.com/auth/calendar`; у списку тестових
   користувачів (Audience) додати свою адресу Gmail.
4. Clients → Create client → тип **Desktop app**. Отримаєш Client ID і
   Client secret.
5. Передати їх під час збірки:
   ```bash
   cmake -B build -DCMAKE_BUILD_TYPE=Release \
         -DLOWACAL_GOOGLE_CLIENT_ID="....apps.googleusercontent.com" \
         -DLOWACAL_GOOGLE_CLIENT_SECRET="..."
   ```
   Або спробувати без перезбірки: `env LOWACAL_GOOGLE_CLIENT_ID=... LOWACAL_GOOGLE_CLIENT_SECRET=... lowacal`

(Назви пунктів у консолі Google час від часу міняються; суть кроків та сама.)

Що треба знати про обмеження Google (за їхньою документацією):
- Поки проєкт у статусі **Testing**: входити можуть лише додані вручну
  тестові користувачі (до 100), і вхід **злітає кожні 7 днів** — застосунок
  тоді прямо каже увійти знову.
- Статус **In production без перевірки**: вхід не злітає, але користувачі
  бачать попередження «застосунок не перевірено», і діє ліміт 100
  користувачів загалом.
- Для справжнього публічного релізу Google має **перевірити застосунок**
  (verification): це вимога для застосунків із чутливими дозволами, до яких,
  наскільки відомо, належить і календар. Точний перелік вимог дивись у Google.
  Подати заявку може лише власник проєкту.
- «Client secret» десктопного застосунку Google секретом не вважає (він
  є в кожній копії програми), тому вхід захищено PKCE. Чи класти ці
  ідентифікатори у публічний репозиторій, вирішуєш ти; для Flathub вони
  так чи інакше мають бути в маніфесті.

Перевірено: увесь шлях (вхід, PKCE, обмін коду, оновлення токена,
синхронізація з Bearer-токеном, відкликаний доступ) проходить наскрізний
тест проти `tests/fake_google.py`, який перевіряє те саме, що й справжній
Google. Проти справжнього Google ще не запускалось: для цього потрібні
ідентифікатори з кроків вище.

**Міграція зі старої версії:** якщо був `~/.config/lowacal/accounts.json`
і пароль через `secret-tool`, перший запуск сам перенесе акаунт і пароль у
нове сховище, а файл перейменує на `accounts.json.imported`.

## Мова інтерфейсу

Вихідна мова коду — англійська (стандарт для Flathub і KDE), переклади
лежать у `i18n/` (зараз `lowacal_uk.ts` — українська). За замовчуванням
мова береться із системи; в Налаштуваннях її можна вибрати явно
(«Як у системі» / English / Українська), застосовується після
перезапуску. Назви місяців і днів, формат дат беруться з тієї ж мови, тож
граматика правильна: «Липень 2026» у заголовку, «17 липня» в даті.

Додати мову: скопіюй `i18n/lowacal_uk.ts` як `lowacal_<код>.ts`, додай
його в `TS_FILES` у `CMakeLists.txt` і переклади (зручно в Qt Linguist:
`linguist i18n/lowacal_<код>.ts`). Після зміни рядків у коді:
`cmake --build build --target update_translations`.

## Тести

```bash
cmake -B build -DLOWACAL_BUILD_TESTS=ON && cmake --build build
./build/lowacal_logic_test          # ICS/SQL/XML-парсинг
tests/run_ui_flow_test.sh build     # автозапуск, одна копія, і наскрізний тест інтерфейсу трьома мовами
```

`run_ui_flow_test.sh` піднімає фейковий Nextcloud-подібний CalDAV-сервер
(`tests/fake_caldav.py`) та ізольоване сховище паролів, і проганяє
додавання акаунта як користувач: невірний пароль, недоступний сервер,
успішне підключення з автопошуком адреси, синк подій, перезапуск,
налаштування, видалення. Нічого з реальних даних користувача не чіпає.
Потрібні `python3`, `dbus-run-session`, `gnome-keyring`.

## Що працює / Що ще ні

**Оновлення 2 — після діагностики через LOWACAL_DEBUG_DUMP (сирі дампи
реальних відповідей iCloud):**
- **Кольори календарів** — корінь знайдено у реальному XML: iCloud
  повертає `calendar-color` ДВІЧІ на кожен календар — справжнє значення
  у 200 OK propstat і порожню заглушку у 404 propstat (для неймспейсу,
  який сервер не підтримує). Парсер брав будь-який, і порожній затирав
  справжній. Виправлено (порожнє значення більше ніколи не перезаписує
  знайдене) + тест на точній структурі з реального дампу.
- **"46 подій синкнулось, 5 показується"** — корінь: у реальних даних
  різні події (різні `href` — серверний унікальний ідентифікатор
  ресурсу) можуть мати ОДНАКОВИЙ iCalendar `UID`. Моє початкове
  припущення, що це один UID на майстер+винятки повторюваної події,
  було невірним — це просто events з дубльованими UID. Схема
  переписана: ключ тепер `(href, calendar_id)`, а не `(uid, ...)` —
  href гарантовано унікальний сервером, UID (як показали живі дані) ні.
  Всі точки (parse → store → notify → create) оновлені відповідно,
  з тестами на точний сценарій "різні href, однаковий UID".
- **День/Тиждень** — реалізовано (`WeekDayGrid.qml`): погодинна сітка,
  події позиційовані за часом і тривалістю, all-day стрічка зверху,
  підсвітка сьогодні, той самий попап деталей. Перемикач День/Тиждень/
  Місяць тепер реально перемикає вигляди, стрілки навігації і заголовок
  крокують днем/тижнем/місяцем відповідно до режиму.
- Дрібне: чистий teardown фонового потоку (таймери зупиняються на
  своєму потоці, без Qt-ворнінгів при виході).

**Діагностика для майбутніх загадок:** `LOWACAL_DEBUG_DUMP=1 ./lowacal`
пише всі сирі WebDAV-відповіді у `/tmp/lowacal-debug/` — вимкнено за
замовчуванням (там особисті дані календаря).

**Оновлення 1 — після першого реального синку з живим iCloud:**
спрацювало наскрізь — discovery, фетч подій, створення нової події з
застосунку дійшло до iPhone. Виправлено: UNIQUE constraint збій, що
обнуляв цілий календар (тепер неактуально після href-рефакторингу вище);
запит кольору у двох неймспейсах; FREQ=YEARLY події (дні народження)
зсуваються в поточний рік, щоб узагалі показуватись (повного RRULE досі
нема — це свідомо).

Працює (скомпільовано, ICS/SQL/XML-парсинг покритий 40+ тестами, CalDAV
підтверджений живим iCloud):
- Discovery + синк подій з CalDAV (iCloud, будь-який CalDAV-сервер з Basic auth)
- Локальний кеш у SQLite (ключ — серверний href), миттєвий UI, push-оновлення
- Нотифікації за 10 хв до події (QSystemTrayIcon::showMessage)
- Трей, hide-not-quit, ручний "Синхронізувати зараз"
- Місяць / Тиждень / День вигляди, локаль-залежний перший день тижня
- Кольори календарів з сервера
- Створення нової події ("+" → форма → ICS → PUT на сервер → локальний кеш)
- FREQ=YEARLY (дні народження) показуються в поточному році

Свідомо не в v1:
- Редагування/видалення вже існуючих подій
- Повна підтримка `RRULE` (тижневі/місячні повторення, винятки) — тільки
  перше входження, крім спеціального випадку `FREQ=YEARLY`
- Власні часові пояси з VTIMEZONE (стандартні назви на кшталт Europe/Kyiv працюють)
- Ручна зміна кольору календаря (зараз колір береться з сервера)
- Windows-порт
